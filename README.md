# Quality Lab 0.2 — Spotify 9.2.2 experiment

实验插件，不是已验证的超高／无损解锁。编译仅在 GitHub Actions macOS runner 执行；没有在本地编译或测试。只依赖系统 Foundation/UIKit，可用全能签向解密的 9.2.2 IPA 注入 `QualityLab.dylib`，然后重新签名安装。安装成功与音质解锁是两项独立结果。

## 手机验证

1. 使用原始 IPA 注入此 dylib，不叠加其他修改插件。保留原包用于恢复。
2. 启动后点击右上角 QL。默认只观察。打开系统音质页，播放一首歌，导出一次日志作为基线。
3. QL → 启用属性修改，从后台完全退出后重开。打开音质页，记录 Premium 提示是否变化。
4. 优先通过原生音质页选择超高。若仍受限制，可用 QL 的“尝试超高：枚举 4”直接调用原生偏好。重新进入音质页核对实际选中的标签。当前 3/4/5 枚举来自旧版接口线索，9.2.2 的映射必须由这一步验证，不能把读回 4 直接当成 320 kbps。
5. 切换到一首没有下载和缓存的曲目，播放 30–60 秒，记录能否播放、卡顿或自动降级。导出日志，再独立尝试枚举 5。没有缓存的曲目也不能仅凭流量大小判定格式。
6. 把两次日志和音质页截图反馈。日志中的 `account LOCAL_INPUT` 是当前本地接口的输入，可能已包含之前的本地修改，不能当成服务端原始响应；`READBACK` 只是偏好设置；`player METADATA` 是客户端报告的播放元数据，尚未独立验证。没有实际音源格式证据时，结论只能是“未知”。
7. 恢复时选择“写入高：枚举 3”，并在 Spotify 原生音质页核对后关闭属性修改、完全退出重开。彻底移除插件可用原始 IPA 重新签名安装。

## 实现与限制

- 仅匹配可执行文件 Spotify、版本 9.2.2，运行时核对每个目标方法的 ABI；缺失方法记录并跳过。
- 默认保留账号读值。实验模式仅改变本地 `type/product/catalogue` 与 `high-bitrate/very-high-bitrate` 的读值，没有伪造服务端响应、音质标识、播放元数据或采样率。
- 捕获原生偏好对象，显式调用蜂窝及 Wi-Fi 播放音质 setter，记录读回值。不修改下载音质或自动禁止降级。
- 观察播放器 track metadata 中固定允许的音频字段，不记录 URL、凭证、账号 ID 或曲名，不发送任何日志到网络。
- 此第一版尚未观测 C++ 播放核心、Nebula/Protobuf 账号属性或音源解码器；如果修改不影响界面或播放，需要依据实测日志继续定位，不能直接认定服务端拒绝。播放器 metadata 中的 lossless 字段同样不能独立证明编码格式。
- GitHub 构建与签名检查验证的是产物结构，不能替代 iPhone 安装和播放测试。

接口定位参考（仅用于找到实验入口，不把项目结论当实测结果）：[EeveeSpotifyReincarnated](https://github.com/SideloadLabs/EeveeSpotifyReincarnated/tree/cb21e44da3da715c17cc23c5cf76a93728958b1a)。此项目是独立编写的 Objective-C 实验，没有引入第三方插件二进制。

## 0.2 诊断改进

第一轮手机日志确认属性修改模式已启动，两个播放偏好写入 4 后即时读回 4，但重开音质页仍显示自动。0.1 的全局去重会漏掉 0 → 4 → 0 的最后一次变化，不能据此判断值是否持久化。0.2 改为按对象和字段只去掉连续相同值，记录偏好对象身份；新增“读取当前状态”，每次写入后立即、5 秒、20 秒及导出前都记录无去重快照。导出还包含相关类的接口名称和 ABI，不调用未知接口。没有新增音质修改策略，以便单独核查状态变化。
